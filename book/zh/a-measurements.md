# A. 测量
<!-- 译自 5c9c39e -->

本书的基准测量来自 `examples/bench`。这是一个测量框架（harness），它生成一个合成 Go 仓库，在一组
固定的场景中用两种工具构建并测试它，并记录每一条命令。[^a-main]

## 合成仓库

![图 A.1：包数为 1000 时生成的导入图。包只导入更低层的包或 `core`，二进制只导入最顶层的包。](../figures/a-repository.svg)

`bench gen` 写出一个 Go 模块，连同 Gazelle 会为它写出的 BUILD 文件，因此两种工具构建的是同一棵源码树；
给定的形状总是产生相同的字节。[^a-gen]包均匀地分布在各层中（图 A.1）。第 0 层以上的每个包从
紧邻的下一层中随机选择至多三个包导入，再从任意一个更低的层中导入一个包：扇入（fan-in）为四。[^a-plan]
0 号包 `core` 位于第 0 层，其余每个包还以 0.3 的概率直接导入它，因此对 `core` 的修改会波及仓库的大部分。
二进制每 100 个包一个，至少两个，每个二进制导入最顶层的三个包。叶子包（leaf）是 `app00` 导入的第一个包，
没有任何库导入它。

每个包都有相同的文件。[^a-files]`edit.go` 中是 `bodyEdit`，一个大到无法内联的函数，测量框架修改的正是
它的函数体。另有三个文件各含十个函数；`api.go` 中的 `Compute` 调用这些函数以及每个被导入包的
`Compute`；`pkg_test.go` 含有两个小测试。每十个包中有一个还带有 `table.txt`，由生成器
`tools/gentable` 将其转换为 `table_gen.go`，代表 protoc 这类生成器。对 go 命令而言，这个文件提交到
仓库中，由 `go generate` 更新；对 Bazel 而言，由一个 `genrule`（运行一条命令的规则）在构建过程中生成
它。[^a-gentable]

各个配置以包数命名：`n100`、`n1000`、`n3000` 和 `n10000`，分别有 8、12、14 和 16 层。[^a-configs-run]
另有两个配置在 1000 个包上改变形状：`n1000-wide` 有 4 层，扇入为 8；`n1000-deep` 有 40 层，扇入为 3。
`n1000-local` 只用 Bazel 构建 `n1000`，并使用 `--spawn_strategy=local`，它把每个动作作为普通的本地进程
运行，[^bazel-spawn]不在沙箱（sandbox，只含一个动作所声明输入的目录）中。

## 测量框架

`bench run` 依次测量每个配置，每种工具都从一棵新生成的源码树开始。[^a-run]当
`-o` 指定一个目录时，`go build` 只构建 main 包及其导入的包；Bazel 则构建 `build_targets.txt` 列出的
目标，即各个二进制和生成器。[^a-targets]

两者都使用 Go 1.27.3：go 命令来自 `-goroot` 指定的 SDK（软件开发包），设置 `GOTOOLCHAIN=local`（不切换到其他 Go 版本），其余
每个 `GO` 变量都由测量框架清除或设定；[^a-goenv][^go-toolchain-local]rules_go 则下载生成的 `go.mod`
所指定的版本（第 2 章）。[^rg-from-file]

在测量框架的工作目录中，每个配置都有自己的 GOCACHE（go 命令的构建缓存）和自己的 Bazel 输出根目录
（output base，存放一个检出的输出与状态的目录）；`--nohome_rc` 和 `--nosystem_rc` 排除用户和系统的
`.bazelrc` 文件。[^a-bazel][^bazel-rc]Bazel 的冷构建在获取 rules_go 和 Go SDK 之后进行，因此不下载
任何内容。

下表中，go 的构建指 `go build -x -o <dir> ./...`，其中 `-x` 打印它运行的每条命令；Bazel 的构建指
`bazel build --target_pattern_file=build_targets.txt`。测试场景在各项修改之后运行，此时构建缓存是热的。

| 场景 | go 命令 | Bazel |
|---|---|---|
| `cold` | 用空的 GOCACHE 构建 | 在 `bazel clean` 和 `bazel shutdown` 之后构建；后者停止服务进程（server，即 Bazel 保存构建图的长期运行进程） |
| `noop` | 再次构建，没有任何改动 | 同上，服务进程保持运行 |
| `noop-discard` | `go build -x ./...`：构建每个包，每个二进制都链接到一个临时目录中，然后丢弃 | — |
| `noop-cold-server` | — | 在 `bazel shutdown` 之后构建 |
| `analysis-cold-server` | — | 在 `bazel shutdown` 之后运行 `bazel build --nobuild`：只做加载与分析，即读取 BUILD 文件并规划动作的两个阶段 |
| `leaf-body` | 修改叶子包 `bodyEdit` 函数体中的一个数字，然后构建 | 同上 |
| `core-body` | 在 `core` 中做同样的修改 | 同上 |
| `core-api` | 向 `core` 添加一个导出函数，然后构建 | 同上 |
| `core-comment` | 在 `core` 的 `types.go` 的 package 子句上方添加一条注释，使其中每个声明的位置都发生移动，然后构建 | 同上 |
| `test-first` | `go test -x -vet=off ./...` | `bazel test //...` |
| `test-noop` | 再运行一次同样的命令 | 同上 |
| `test-core-body` | 先做一次 `core-body` 修改，再运行同样的命令 | 同上 |
| `codegen-generate` | 在一个 `table.txt` 末尾追加一行，然后运行 `go generate ./...` | — |
| `codegen-build` | 接着构建 | 做同样的修改，然后构建 |
| `clone-warmcache` | 把源码树复制到新路径；用同一个 GOCACHE 构建副本 | — |
| `clone-warmcache-trimpath` | 用 `-trimpath`（它从输出中去除文件系统路径）构建原树，不计时；然后同样用 `-trimpath` 构建副本 | — |
| `clone-diskcache` | — | 在 `bazel clean` 之后，用新的磁盘缓存（`--disk_cache`，存放动作结果的本地目录）构建原树，不计时；然后用新的输出根目录和这个缓存构建副本 |
| `server-heap-after-build`、`-test` | — | 在构建场景之后和测试之后运行 `bazel info used-heap-size-after-gc` |

两种工具的先后顺序在配置之间交替，因此没有哪一种总在温度更高的机器上运行。[^a-order]一次测量是一条命令
从启动到退出的墙钟时间。测量框架统计 go 命令 `-x` 输出中的 compile、link、asm 和测试进程，并读取 Bazel
的汇总行，其中给出运行的进程数和由缓存应答的动作数。[^a-time]热场景重复 `-reps` 次，此处为三次；Bazel
的第四次 `noop` 用于让服务进程重新变热，不计入结果。修改在各次运行之间累积。go 命令的冷构建还写出它的
动作图（`-debug-actiongraph`：其中的动作及其耗时）；Bazel 的冷构建、第一次 `core-body` 构建和第一次测试
则写出追踪剖面（trace profile，`--profile`）；第 5 章和第 9 章分析了这些文件。

对 `n1000` 和 `n3000`，在两种工具都测完之后，测量框架再从空的 GOCACHE 开始构建并测试一次，此时 go 命令
运行一个包装程序 `bench toolexec`，即探针（probe），代替每个工具（`-toolexec`）和每个测试二进制（`-exec`）。[^go-toolexec][^go-exec]
包装程序把每个进程的墙钟时间、用户态与内核态 CPU 时间以及峰值 RSS（resident set size，常驻内存集：进程在
同一时刻占用的最多物理内存）追加到 `workload.jsonl`。[^a-probe]它为每个工具多加了一个进程，因此笔者不把这些运行的耗时
与其他运行相比较。

耗时更长（表 A.7）。

## 局限

- **一台机器，且并不空闲**：一台 18 核、64 GB 内存的 Apple M5 Pro，运行 macOS 26.6，[^a-meta]与笔者的
  其他工作共用，[^a-second]例如 `go test -race`。表 A.5 中的变体之后在机器负载较低时重新运行过。[^a-results]
- **合成仓库**：包的结构都相同，没有 cgo，没有外部模块，测试几乎什么都不做，代码生成器只有一个。笔者
  预计，与具体的数字相比，结果的形态更能推广到真实仓库。
- **只有本地 Bazel**：没有远程缓存或远程执行。本地磁盘缓存代替了共享缓存，不含网络时间。
- **macOS**：第 5 章推断，macOS 对新启动应用的检查[^apple-xprotect]拖慢了每个新测试二进制的首次运行。
- **整毫秒**：第一次运行的探针把每个进程的时间向下取整到整毫秒，因此最短的进程读数偏低；探针现在保留到
  微秒。[^a-probe]
- **运行次数少**：每个场景至多三次。`n1000` 与 `n10000` 的第二次运行（表 A.7）与第一次相比，三次运行的
  中位数之比至多为 1.25（例外是 10000 个包时 go 命令的空构建与叶子包修改，比值分别为 2.4 和 3.7），
  其余单元格之比至多为 1.7。[^a-second]

## 复现

测量框架需要 Go 1.27.3、bazelisk（它读取 `.bazelversion` 并下载 Bazel 9.3.2），以及运行分析脚本所需的
`uv`。在仓库根目录下运行：

```bash
GOBIN="$PWD/.tools/bin" go install github.com/bazelbuild/bazelisk@v1.30.0
cd examples/bench
go build -o ../../.tools/bin/bench .
../../.tools/bin/bench gen -pkgs 1000 -o /tmp/synth    # one repository, to inspect
out=results/new    # bench run appends to -out's records; the book's are in results/2026-11-16*
flags=(-reps 3 -work work -goroot "$(GOTOOLCHAIN=go1.27.3 go env GOROOT)"
       -bazel "$PWD/../../.tools/bin/bazelisk")
../../.tools/bin/bench run -configs n1000,n100,n3000,n1000-wide,n1000-deep,n1000-local,n10000 \
    "${flags[@]}" -out $out
../../.tools/bin/bench run -configs n1000-wide,n1000-deep,n1000-local \
    "${flags[@]}" -out $out-variants
for c in n1000 n10000; do   # the second run, sampling the machine's load every 30 s
  mkdir -p $out-$c-check
  while :; do
    echo "$(date +%T) $(sysctl -n vm.loadavg) cpu%=$(ps -Ao pcpu= | awk '{s+=$1} END {printf "%.0f", s}')"
    sleep 30
  done > $out-$c-check/load.log &
  ../../.tools/bin/bench run -configs $c "${flags[@]}" -out $out-$c-check
  kill $!
done
uv run analyze.py --appendix $out $out-variants --second $out-n1000-check $out-n10000-check
```

`bench run` 把各条记录、动作图和剖面写到 `-out` 目录，并把每条命令的输出写到
`work/logs`。[^a-run]不带 `--appendix` 时，`analyze.py` 输出第 5 章的表，并重绘该章的图。
